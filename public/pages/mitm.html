Man In The Middle

Contexte

Une attaque Man In The Middle consiste à s’interposer entre deux systèmes qui communiquent afin d’écouter ou modifier les données en transit. Les victimes pensent échanger directement alors qu’un tiers contrôle le chemin.

Cette page se limite à expliquer le concept, les techniques courantes et les pistes de détection ; il n’y a pas de démonstration ni d’exercice de labo ici.

Points clés

Les attaques MITM exploitent surtout des communications mal protégées ou des configurations réseau faibles. Les techniques peuvent passer par l’empoisonnement ARP, le spoofing DNS ou l’interception de flux non chiffrés.

Pour limiter le risque, il faut privilégier le chiffrement, valider les certificats, segmenter le réseau et surveiller les anomalies de trafic.

En bref

Le MITM rappelle qu’une communication non sécurisée peut compromettre des identifiants et des données sensibles. La protection repose sur la sécurisation des protocoles et une hygiène réseau rigoureuse.

Vue d’ensemble

En MITM, l’attaquant se place entre des extrémités légitimes (utilisateur et service, client et serveur) pour intercepter, modifier ou rediriger le trafic. Il peut espionner des identifiants ou des données de carte bancaire, ou injecter du contenu malveillant. La menace est d’autant plus forte que le chiffrement ou l’authentification est faible ou absente.

Les grandes étapes côté attaquant sont en général :

  • Interception : s’insérer dans le flux (faiblesses de protocoles, ARP spoofing, DNS spoofing, usurpation d’IP, point d’accès Wi‑Fi rogue, etc.).
  • Manipulation / déchiffrement : lire ou altérer la communication, tenter de dégrader le chiffrement (ex. SSL stripping), injecter des réponses falsifiées.

Détecter un MITM demande souvent une approche en couches : supervision réseau, validation des certificats, analyse comportementale et corrélation des journaux.

Types d’attaques souvent cités

  • Capture de paquets sur un réseau partagé ou Wi‑Fi ouvert, surtout si le trafic n’est pas chiffré.
  • Détournement de session : réutilisation de jetons de session pour se faire passer pour l’utilisateur.
  • SSL stripping : forcer ou favoriser du HTTP au lieu de HTTPS pour lire ou altérer les données en clair.
  • Spoofing DNS : réponses DNS falsifiées pour rediriger vers un serveur contrôlé par l’attaquant.
  • Usurpation d’IP : paquets forgés pour imiter une machine de confiance.
  • Point d’accès Wi‑Fi malveillant : faire transiter le trafic des victimes par une borne contrôlée par l’attaquant.

MITM et Cyber Kill Chain

Pour analyser un incident, on peut replacer le MITM dans un modèle de chaîne d’attaque (ex. Cyber Kill Chain : reconnaissance, armement, livraison, exploitation, installation, commande et contrôle, actions sur les objectifs). Le MITM est souvent mobilisé surtout aux phases Exploitation et Installation.

En exploitation, l’attaquant abuse de la confiance ou des limites des protocoles (ARP, DNS, etc.) pour s’interposer. En installation, la position « au milieu » peut servir à injecter des charges (exploit navigateur, dropper, RAT) dans des téléchargements ou des flux non protégés. Détecter un MITM est donc un signal fort : l’adversaire est souvent déjà engagé dans les étapes moyennes d’une intrusion.

ARP et ARP spoofing

ARP (Address Resolution Protocol) associe des adresses IP à des adresses MAC sur un réseau local. Une machine demande « qui a telle IP ? » et la bonne machine répond avec sa MAC.

ARP spoofing : l’attaquant envoie de fausses réponses ARP pour associer sa propre MAC à une IP légitime (souvent la passerelle). Le trafic vers la passerelle transite alors par l’attaquant. Cela fonctionne en partie parce qu’ARP n’authentifie pas les annonces : n’importe quel hôte peut envoyer des réponses « is-at » non sollicitées.

Indicateurs utiles lors d’une analyse (captures, journaux) :

  • plusieurs MAC pour la même IP (mappings dupliqués) ;
  • beaucoup de réponses ARP sans requête correspondante (réponses « gratuites » / non sollicitées) ;
  • volume anormal de trafic ARP sur une courte période ;
  • schémas de redirection de passerelle incohérents ;
  • outils comme Wireshark peuvent signaler des doublons d’adresse (arp.duplicate-address-detected, etc.).

En ligne de commande, arp -a permet aussi de repérer des associations IP/MAC incohérentes sur un poste.

DNS et DNS spoofing

DNS traduit des noms (ex. www.example.com) en adresses IP. En spoofing DNS (ou empoisonnement de cache), l’attaquant fournit une fausse réponse pour qu’un nom pointe vers une IP malveillante — souvent après s’être placé sur le LAN (par ex. via ARP spoofing) pour intercepter les requêtes.

Indicateurs possibles :

  • plusieurs réponses contradictoires pour la même requête ;
  • réponse DNS provenant d’un résolveur inattendu (pas celui configuré) ;
  • TTL anormalement courts (quelques secondes) pour forcer le renouvellement de l’entrée falsifiée ;
  • réponses sans requête cliente visible correspondante.

SSL stripping

Le SSL stripping consiste à intercepter le trafic et à empêcher ou retirer l’usage du chiffrement TLS entre le client et le serveur légitime, souvent en relayant en HTTP vers la victime tout en gardant une session HTTPS côté serveur. Les identifiants ou données sensibles peuvent alors transiter en clair côté client.

Indicateurs possibles dans les captures :

  • requête initiale vers le port 443 puis bascule rapide vers du trafic HTTP (port 80) pour le même site ;
  • redirections HTTP répétées (codes 301/302) depuis des URLs HTTPS ;
  • échecs ou alertes de certificat si l’attaquant proxyfie de façon plus visible.

Une chaîne d’attaque typique en entreprise peut enchaîner : empoisonnement ARP sur la passerelle → réponses DNS falsifiées vers un domaine interne → connexion de la victime vers l’attaquant avec stripping SSL et capture d’identifiants en clair sur HTTP.

Scénario type (investigation)

Les formations type « détection MITM » présentent souvent un fil conducteur : alerte sur un LAN d’entreprise, analyse de captures (.pcap) et de journaux centralisés (par ex. dans un SIEM comme Splunk), recherche des trois briques ci-dessus — ARP, DNS, puis preuves de dégradation TLS — pour reconstituer la chronologie et les indicateurs de compromission.

Les prérequis habituels incluent une base sur Wireshark, les fondamentaux de sécurité réseau et la découverte / détection sur les réseaux.

Résumé détection

  • ARP : doublons MAC/IP, réponses gratuites, anomalies dans le cache ARP.
  • DNS : réponses multiples ou depuis des sources non prévues pour un même nom.
  • SSL stripping : données sensibles en clair sur HTTP là où HTTPS est attendu, ou disparition des négociations TLS vers le vrai serveur.

En analyse de captures, des filtres d’affichage courants isolent les protocoles concernés (ex. arp, dns, tls || ssl, http) ; on peut affiner sur les opcodes ARP, les drapeaux DNS « réponse », ou le SNI TLS pour un nom d’hôte précis.
