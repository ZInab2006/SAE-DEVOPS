Services Firebase Utilisés

🧭 Contexte

Dans le cadre de la SAE DevOps (BUT2), le sujet impose de rendre le site accessible sur le web et d’exploiter l’écosystème Google Firebase. Notre blog « CyberNotes » est un site entièrement statique : HTML, CSS et JavaScript servis tels quels, avec un routeur côté client qui charge les fragments de pages dans une seule index.html. Pour ce type d’architecture, Firebase Hosting est le service adapté : il expose nos fichiers sur le réseau avec HTTPS, un déploiement rapide et un plan gratuit (Spark) suffisant pour un projet pédagogique.

Nous n’avons pas activé d’autres produits Firebase obligatoires pour cette SAE (Authentication, Firestore, etc.) : le périmètre se concentre sur la mise en ligne, la reproductibilité des déploiements et la cohérence entre le dépôt Git et ce qui est visible en production. Cette page documente précisément ce que nous avons branché, comment c’est configuré, et ce que ça apporte au groupe.

🛠️ Ce que nous avons mis en place

Voici les éléments concrets présents dans le dépôt et utilisés pour publier le site.

  • Firebase Hosting : le répertoire public/ est défini comme racine du site. Tout le contenu visible (pages, CSS, JS, images) part de ce dossier. Les visiteurs accèdent à une URL unique ; le menu et le routeur JavaScript affichent ensuite les bonnes « pages » sans rechargement complet, ce qui reste compatible avec un hébergement statique.
  • Routage SPA : dans firebase.json, une règle de rewrites renvoie toutes les routes vers /index.html. Ainsi, un lien du type ?page=labo1/search-skills ou un rafraîchissement du navigateur ne provoque pas une erreur 404 côté serveur : c’est le comportement attendu pour une application à page unique.
  • Configuration projet : le fichier .firebaserc associe l’alias default à l’identifiant du projet Firebase du groupe. Chaque membre qui déploie utilise le même projet après firebase login, ce qui évite les décalages entre environnements. Le fichier firebase.json complète la définition : dossier public, fichiers ignorés au déploiement (node_modules, fichiers cachés, etc.).
  • Déploiement : la publication se fait avec la CLI officielle (firebase deploy ou ciblage du hosting uniquement). Le workflow est reproductible : pull du dépôt, vérification en local si besoin (npx serve public), puis déploiement. Le dépôt peut aussi s’appuyer sur des workflows GitHub (fichiers sous .github/workflows/) pour automatiser les déploiements lors des fusions sur la branche principale, ce qui relie directement notre flux Git aux mises en ligne.

✨ Synthèse

Firebase Hosting répond clairement au cahier des charges : site public, HTTPS, simplicité pour une équipe qui n’a pas à gérer un serveur dédié. La configuration reste légère (deux fichiers à la racine et un dossier public), ce qui facilite la reprise par un autre membre ou l’évaluation du projet.

Pour la suite, l’équipe peut enrichir le pipeline (tests avant déploiement, prévisualisations sur pull request) sans changer de plateforme d’hébergement. L’essentiel est déjà en place : une base stable pour présenter les labs, les ressources SAE et le travail collectif, avec un déploiement aligné sur les bonnes pratiques DevOps vues en cours.
